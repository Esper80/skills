# GitHub PR·리뷰·CI

권한과 검증 기준은 [전달 계약](delivery-contract.md)을 따릅니다. 필요한 단계만 수행합니다.

## PR 작성·갱신

- 현재 변경·브랜치·base와 올바른 원격을 확인합니다. 기준이 오래됐거나 충돌이 의심되면 해당 원격 ref를 fetch하고 실제 SHA를 대조합니다. 항상 최신 base로 이력을 재작성할 필요는 없습니다.
- 목적별 커밋으로 구성하고 개인 설정·로컬 데이터·비밀값은 제외합니다. 여러 저장소라면 각각의 PR이 호환 가능한 중간 상태를 유지하도록 계약·전달 순서를 설명합니다.
- PR 언어·이해도는 전역 사용자 지침을 따릅니다. 문제와 결과 동작, 중요한 검증·제한, 필요한 배포·복구 정보를 적고 세부 정도는 변경에 맞춥니다.
- 기존 라벨 중 직접 관련된 것만 선택합니다. 새 라벨을 임의로 만들지 않습니다. 담당자는 프로젝트 규칙을 따르고 기존 담당자를 보존합니다.
- `gh`로 여러 줄 본문·댓글을 작성할 때 실제 줄바꿈이 있는 파일과 `--body-file`을 사용합니다. 구조화된 도구 인자도 적합합니다.
- 생성·갱신 뒤 본문·라벨·base/head·상태를 확인합니다. 생성한 PR은 `attach_artifact`가 사용 가능하면 현재 채팅에 연결합니다.

## 리뷰·CI 대응

- review thread의 `isResolved`, `isOutdated`, 파일·라인과 현재 head의 코드를 함께 확인합니다. 현재 남은 actionable 지적을 처리하고 오탐·취향·범위 밖 요청은 근거를 남깁니다.
- 같은 원인의 관련 경로를 필요한 범위에서 조사하고 수정·검증합니다. 승인된 댓글·해결 처리는 처리 결과가 준비되면 진행하며, 새 CI를 기다릴 필요만으로 미루지 않습니다.
- 필수 체크와 실제로 요청·설정된 리뷰의 완료를 함께 확인합니다. 알려진 actionable 리뷰를 발견하면 CI 대기보다 대응을 우선합니다.
- 고정 `30초×20회` 대기나 사용하지 않는 모든 봇의 응답은 요구하지 않습니다. 저장소 정책·진행 중 리뷰에 맞춰 기다리고 상태가 바뀌지 않으면 조회 간격을 늘립니다. 요청한 단계의 필수 검사와 리뷰 처리가 끝나면 확인을 종료하고, 완료 이후 지속 감시는 별도 요청이 있을 때만 수행합니다. 필수 검사·리뷰가 남아 있으면 완료로 보고하지 않습니다.
- 최신 head와 관련된 결과를 사용합니다. head 변경이 검사한 동작에 영향을 주면 필요한 검증·리뷰만 갱신합니다. reaction 하나나 깨끗한 스레드 목록만으로 통과를 판단하지 않습니다.
- 실패한 check와 head, run URL, 핵심 로그로 변경 결함·외부 장애·불안정한 테스트를 구분합니다. 근거 없이 재실행을 반복하지 않습니다.

## 충돌과 병합

- 충돌을 발견하면 게시·병합에 앞서 양쪽 의도와 현재 사용자 변경을 보존해 해결합니다. `ours`/`theirs`를 맹목적으로 선택하지 않습니다.
- 승인된 로컬 준비 범위에서 비파괴적 충돌 해소를 진행할 수 있습니다. 공유 이력 재작성이나 force-push가 필요하면 해당 권한을 확인합니다.
- 병합 가능 판단은 현재 head의 필수 검사·필수 리뷰·미해결 actionable thread·mergeability 및 필요한 base 최신화 조건을 근거로 합니다. 정책이 요구하지 않는 무조건적인 rebase는 하지 않습니다.
- 병합은 승인된 경우에만 저장소 방식으로 수행하고, 직전 관련 head·체크 상태를 확인합니다. 결과가 바뀌었다면 병합을 보류하고 영향을 평가합니다.
- 병합 후 PR 상태와 원격 base의 반영을 확인합니다. 배포까지 요청됐다면 실제 배포 결과와 검증 후보·실제 병합 SHA·운영 활성 SHA의 대응을 확인합니다. 병합·결합으로 코드가 달라졌다면 영향을 받은 검사만 갱신합니다. 완료 후 지연 봇 리뷰를 반복 대기하지 않습니다.
- 여러 저장소는 승인된 순서와 최종 계약에 맞춰 전달합니다. 앞선 변경으로 계약이 달라지면 뒤 PR에 영향을 평가하고 필요한 수정·검증을 갱신합니다.
