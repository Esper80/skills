# 저장소별 단독 PR과 분할 커밋 규칙

## 1. 입력 수집

- `git status --short --branch`로 현재 브랜치와 미커밋 변경을 확인한다.
- `git log --oneline --decorate --graph <base>..HEAD`로 로컬 커밋을 확인한다.
- `git diff --stat <base>...HEAD`, `git diff --name-status <base>...HEAD`로 변경 범위를 본다.
- 현재 후보와 같은 작업·브랜치·공유 자원에 관련된 worktree의 `git status --short --branch`를 확인한다. 전체 목록(`git worktree list`) 조회는 후보 식별이나 충돌 확인에 필요한 경우에만 수행한다.
- task 파일, 계획 문서, 이력 문서가 있으면 요구사항과 이미 적용된 범위를 대조한다.

## 2. 저장소별 단독 PR 기준

같은 작업은 아래 기준으로 그룹화한다.

- 한 저장소에서 발생한 같은 작업의 변경은 PR 하나에 모은다.
- 여러 저장소를 변경하면 저장소마다 브랜치와 단독 PR 하나를 만든다.
- 같은 저장소의 기반, 스키마, API, 기능, UI, 배포, 문서 변경을 의존성 단계별 여러 PR로 나누지 않는다. PR 내부의 논리적 커밋으로 구분한다.
- 기능 코드, 직접 테스트, 필요한 문서와 검증 스크립트는 같은 저장소 PR에 둔다.
- 각 저장소 PR은 단독 merge 후 해당 저장소의 빌드, 테스트, 배포 파이프라인을 깨뜨리지 않아야 한다.
- 다른 저장소 PR이 나중에 배포되더라도 안전하도록 하위 호환, feature flag, no-data 처리, 또는 명시적인 producer-first/consumer-first 순서를 설계한다.
- 각 저장소 PR은 관련 저장소 PR보다 먼저 또는 나중에 merge·배포될 수 있음을 전제로, 기존 계약을 깨뜨리지 않는 호환 가능한 중간 상태여야 한다. 다중 저장소 기능의 최종 활성화와 사용자 노출은 PR 본문에 명시한 rollout 순서를 따른다.
- 로컬 전용 파일, 개인 환경 설정, 운영에 올리지 않을 런타임 데이터는 운영 PR에서 제외한다.
- 변경이 크더라도 같은 저장소의 단일 작업이면 PR 하나를 유지하고, 리뷰와 실패 원인 추적은 커밋 경계와 PR 본문으로 지원한다.
- 같은 저장소를 여러 PR로 나누는 예외는 사용자의 명시적 요청, 저장소 강제 정책, 또는 확인된 플랫폼 제한이 있을 때만 허용하며 사유를 보고한다.

## 3. 권장 논리적 커밋 순서

커밋은 저장소 관례와 실제 의존성에 맞춰 아래 순서를 조정한다.

1. **호환 가능한 기반**: 스키마 expand, API contract, 권한, 보안 가드처럼 뒤 커밋이 의존하는 변경과 직접 테스트.
2. **기능 구현**: 서버, 도메인, exporter, consumer 로직과 직접 테스트.
3. **UI/UX 또는 운영 연결**: 화면, 대시보드, 배포 설정, provisioning과 직접 검증.
4. **독립 검증 보강**: 공통 테스트 구조나 CI 보조 스크립트처럼 특정 기능 커밋에 귀속되지 않는 변경.
5. **문서/운영 절차**: rollout, rollback, 환경 변수, Wiki 또는 운영 문서.
6. **정리**: 같은 PR에서 안전하게 끝낼 수 있는 deprecation이나 dead code cleanup. 소비자 전환 전 삭제는 넣지 않는다.

각 커밋은 하나의 설명 가능한 목적을 가져야 하며 기능과 직접 테스트를 가능하면 같은 커밋에 둔다. 중간 커밋이 의도적으로 완전한 배포 단위가 아닐 수는 있지만, 가능하면 build와 기본 정적 검사를 깨뜨리지 않도록 구성한다. merge-ready 판정은 저장소 PR의 최종 `HEAD` 전체 검증으로 한다.

## 3.1 저장소 간 PR 정렬

여러 저장소의 단독 PR이 함께 동작할 때는 다음을 수행한다.

1. 저장소별 최신 base와 worktree 상태를 각각 확인한다.
2. 저장소별 브랜치, 커밋, 검증, PR을 독립적으로 관리한다.
3. producer/consumer, 앱/모니터링, 서비스/인프라 계약과 호환 가능한 중간 상태를 확인한다.
4. 필요한 merge·배포 순서와 순서가 뒤바뀌었을 때의 증상, rollback 경계를 각 PR 본문에 적는다.
5. 먼저 처리된 저장소 PR의 리뷰 대응으로 계약이 바뀌면 아직 열려 있는 관련 저장소 PR을 재검증한다.
6. 같은 저장소의 추가 변경은 merge 전 기존 단독 PR에 새 논리적 커밋으로 반영한다.

## 4. 크기 제한과 CI gate 대응

- 저장소에 `ci:gate` 또는 줄 수 제한이 있으면 저장소별 PR의 `diff --stat`를 보고 초과 가능성을 미리 표시한다.
- 로컬 `ci:gate`/coverage는 통과했지만 원격 또는 운영 CI에서 coverage threshold 차이로 실패하면, 해당 실패를 같은 세션의 이후 검증 기준에 즉시 반영한다.
  - 관측된 하락폭을 safety margin으로 잡고, 다음 로컬 목표를 `공식 threshold + 관측된 하락폭` 이상으로 둔다.
  - 가능하면 0.05~0.1%p 추가 여유를 둔다.
  - 사용자가 특정 프로젝트의 coverage 편차를 알려준 경우에는 첫 실패를 기다리지 말고 그 값을 현재 세션의 PR 로드맵/검증 기준에 반영한다.
  - 이 규칙은 모든 저장소에 고정 적용하지 않고, 관측된 편차 또는 사용자 제공 근거가 있을 때만 적용한다.
- 크기나 리뷰 편의를 이유로 같은 저장소 PR을 바로 나누지 않는다. 먼저 논리적 커밋, PR 본문 목차, 검증 구간으로 가독성을 확보한다.
- 저장소 강제 제한 때문에 여러 PR이 불가피하면 사용자에게 제한 근거와 대안을 보고한 뒤 예외를 적용한다.
- 여러 저장소의 배포 순서를 안전하게 만들기 위해 compatibility shim이나 feature flag가 필요한지 검토한다. 단, 불필요한 미래 확장 계층은 만들지 않는다.

## 5. 로드맵 판단 질문

각 저장소 PR마다 다음 질문에 답한다.

- 이 저장소의 같은 작업 변경이 단독 PR 하나에 모두 포함됐는가?
- 의존성, 기능, 배포 단계를 PR이 아니라 논리적 커밋으로 나눴는가?
- 다른 저장소 PR의 merge·배포 전후에도 안전한가? 순서 제약이 있다면 명확한가?
- 같은 저장소를 여러 PR로 나눴다면 허용된 예외와 사용자 확인이 있는가?
- 이 PR의 테스트가 해당 변경을 충분히 증명하는가?
- 각 커밋이 리뷰와 CI 실패 원인을 좁힐 수 있을 만큼 목적이 명확한가?
- 운영에 올리지 않을 로컬 전용 데이터가 섞여 있지 않은가?
